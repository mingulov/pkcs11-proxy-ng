# v0.3 scope: multi-client isolation and qualification

This is planned work, not a completed feature set or a delivery-date commitment.
v0.2 remains an unreleased testing baseline for one logical client in one trusted
security domain per daemon/provider instance. Do not share it with mutually
untrusted clients. Restart the daemon/provider before changing independent
clients or domains. `max_contexts = 1` is an admission guardrail, not an
isolation fix or proof that native authentication state has been cleared.

Before any multi-client support claim, the planned work includes:

- Object-privacy handling with public/private/unknown state, provider defaults,
  supported attribute encodings, conservative unknown handling, and cache
  invalidation for creation, copy, mutation, destruction and session teardown.
- Login and private-operation admission synchronized through actual native-call
  completion, including timeout/cancellation behavior and orphaned physical
  authentication state. Per-context bookkeeping alone is insufficient.
- Adversarial multi-client validation of identity, object visibility, operation
  authorization, login/logout, teardown and client handover, including failures
  and concurrent native operations. Preserve provider findings and exact RVs;
  do not normalize them to make comparisons pass.
- Candidate-bound provider, platform, transport and native-lifetime qualification
  with portable provenance and explicit completion. Build, stub, load and runtime
  tests retain their distinct scopes; historical receipts do not qualify later
  source automatically.

Implementation and independent review must establish the contracts before the
supported scope expands. Separate daemon/provider instances remain the boundary
for independent domains; shared external HSM/token behavior needs its own
qualification. This roadmap neither removes existing authorization checks nor
claims the deferred issues are repaired by the narrower v0.2 scope.
